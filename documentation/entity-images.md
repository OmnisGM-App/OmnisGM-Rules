# Картинки сущностей — формат и раскладка

Спека к issue #201 (портреты существ) и #202 (генератор, иконки заклинаний и магпредметов). Держится здесь, а не в голове генератора: любой прогон — ручной или из GH Actions — обязан класть файлы ровно так, иначе страница и JSON API их не увидят.

## Формат

| параметр | значение |
|---|---|
| размер | **512×512** |
| формат | **webp** |
| команда | `cwebp -resize 512 512 -q 82 in.png -o out.webp` |
| вес | ~12 КБ на файл (фактический средний по 493 портретам) |
| исходники PNG | **не коммитятся** — только webp |

Размер зафиксирован: он же уходит в `og:image:width/height` и в `width/height` тега `<img>`, а по ним браузер резервирует место (иначе растёт CLS). Файл другого размера сломает и разметку, и превью в соцсетях — при смене размера правится `ENTITY_IMAGE_SIZE` в `web/src/lib/entity-image.mjs`.

## Куда класть

```
web/public/img/{game}/{kind}/{slug}.webp
```

* `{game}` — `dnd`, `daggerheart`;
* `{kind}` — один из пяти видов:

| вид | что внутри | откуда очередь |
|---|---|---|
| `creatures` | монстры, животные, противники | API |
| `spells` | заклинания D&D | API |
| `domain-cards` | карты доменов Daggerheart — его «заклинания» | API |
| `magic-items` | магпредметы D&D; Items и Consumables Daggerheart | API + markdown |
| `gear` | обычное снаряжение: верёвка, рюкзак, меч, доспех | API + markdown |

* `{slug}` — слаг сущности в JSON API, **он же имя файла**, без исключений.

Для существ папка **одна на игру**, а не на коллекцию API. Причина: один слаг живёт в нескольких коллекциях — 83 существа есть и в `monsters` 5.1, и в `animals` 5.2 (в 2024 их вынесли в отдельный раздел), ещё 12 совпадают с `adversaries` Daggerheart. Раскладка по коллекциям означала бы две копии одного файла, а после следующего прогона генератора — два разных портрета у одного существа. Слаг уникален внутри игры, поэтому ключ «игра + слаг» достаточен.

Коллекции с непересекающимися слагами кладутся в свои папки: `img/dnd/spells/`, `img/dnd/magic-items/`, `img/dnd/gear/`. В `gear` сливаются три коллекции API D&D (`equipment`, `weapons`, `armor`) — по той же причине, что и у существ: это один вид вещей, и делить его по коллекциям незачем.

## Два источника очереди

Генератор берёт очередь из **JSON API** там, где коллекция в нём есть, и из **markdown-таблиц `src/`** там, где её нет. Второе — не про удобство: снаряжение и предметы Daggerheart (оружие, броня, Items, Consumables) и оружие с бронёй BRP в API не выведены вовсе, им нужен парсер, а картинки нужны раньше.

В markdown-режиме слаг считает сам генератор — **той же формулой**, что `slugify` в `.github/scripts/parsers/base.py`. Это критично: разойдись формулы, картинки лягут под именами, которых сущности никогда не получат, и никакой ошибки при этом не возникнет — просто на странице не будет картинки. Инвариант стережёт e2e «слаг в генераторе и в парсерах считается одинаково» (431 реальное имя, сверка с настоящим питоновским `slugify`).

Пока коллекции нет в API, картинка лежит заделом: страница её не покажет, поля `image` в API не будет. Как только парсер появится — файлы подхватятся по имени, перегенерация не нужна.

## Кто это читает

* **Страницы** — `web/src/lib/entity-image.mjs`: `entityImage(game, kind, slug)` отдаёт путь или `null` (для существ есть короткий `creatureImage(game, slug)`). Компонент `EntityHead.astro` показывает картинку у заголовка; без файла страница рендерится как раньше, без пустого места.
* **JSON API** — `.github/scripts/generate_api.py`, функция `attach_images()`: ставит поле `image` (абсолютный URL) **только если файл реально есть**. Сущность без картинки поля не имеет вовсе — потребитель (компендиум Table, `og:image`) не должен получать битый URL. Карта коллекций — константа `IMAGE_DIRS` там же; новая коллекция добавляется одной строкой.
* **Схемы** — `image` описан в `MONSTER_SCHEMA` и `DH_STATBLOCK_SCHEMA` как необязательный. У схем стоит `additionalProperties: false`, поэтому **новая коллекция с картинками требует правки своей схемы**, иначе валидация в CI упадёт.

## Кэш

`/img/**` отдаётся с `Cache-Control: public, max-age=2592000` (30 дней) — правило в `firebase.json`, отдельно от глобального правила для картинок.

Намеренно **без `immutable` и без года**: имя файла — слаг без хеша содержимого, поэтому перегенерированный портрет с тем же именем не доехал бы до пользователя, у которого файл уже в браузерном кэше (его, в отличие от edge-кэша, не почистить purge'ем). Тридцать дней дают почти ту же экономию и ограничивают худший случай.

Порядок правил в `headers` **проверяется только на проде**: `/img/**` пересекается с общим правилом `**/*.@(jpg|…|webp|ico)` (сутки), а приоритет совпадающих правил `headers` Firebase не документирует (для `redirects`/`rewrites` — «первое совпадение», для `headers` формулировки нет). Правило для `/img/**` стоит последним. После деплоя проверить фактический заголовок:

```bash
curl -sI https://rules.omnisgm.com/img/dnd/creatures/aboleth.webp | grep -i cache-control
```

Ожидается `max-age=2592000`. Если пришло `86400` — приоритет обратный, правило нужно поднять выше общего.

Отдельно живёт edge-кэш Cloudflare (#175) — см. `web/scripts/check_edge_cache.sh`. При **замене** существующего файла (не добавлении нового) нужен точечный purge, иначе на эдже останется старый портрет.

## Кто это генерирует

`scripts/gen-images.mjs` + воркфлоу `.github/workflows/gen-images.yml` (#202): очередь строится от данных Rules (JSON API), картинки коммитятся по одной в ветку `images-queue`, оттуда draft-PR в `main` без автомёржа. Промты и как перегенерировать одну картинку — [image-prompts.md](image-prompts.md).
