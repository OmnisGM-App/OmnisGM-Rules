## Продукт и экосистема OmnisGM

### Расстановка продуктов
- **Основной** — интерактивный лист персонажа.
- **Доп** — новости (The Guild Herald, news.omnisgm.com; отдельное репо `OmnisGM-News`).
- **Этот** — правила/SRD (`rules.omnisgm.com`).

### Главная цель — SEO-воронка в основной продукт
Человек гуглит уточнение по правилу → попадает на нашу **статичную** страницу правил → CTA уводит его
в интерактивный лист персонажа. Поэтому **SEO критичен** и контент **обязан рендериться в статический HTML**
(НЕ client-rendered SPA — именно client-render убил SEO новостям: краулер видит пустой `<div id=root>`).

### Стек публикации — Astro (SSG)
Публикует сайт **Astro (SSG)**; прежний MkDocs Material + GitHub Pages выведен из эксплуатации
(`pages.yml` удалён). Контентный пайплайн импорта/перевода от движка не зависит — он производит
`.md`, которые потребляет сайт.

Почему Astro: (1) дизайнер отдал готовые **React-компоненты**, и Astro умеет и принять их
островами, и отдать статикой; (2) **PWA обязателен** (first-class `@vite-pwa/astro`);
(3) общий стек с экосистемой. По факту сборки островов не понадобилось: компоненты перенесены
как `.astro`, и страницы уезжают zero-JS — SEO целы по построению.

Остатки MkDocs снесены (#296): `src/site/`, `prepare_docs.sh`, `split_sitemap.py`, записи
`/site/ /docs/ /mkdocs.yml /overrides/` в `.gitignore` и скилл integrate-srd. Мёртвыми они
были не совсем: скилл до #297 стоял фазой в обоих оркестраторах пайплайна и внутри звал
`prepare_docs.sh`, то есть новую систему «интегрировали в сайт» по инструкции для движка,
которого нет. Шаг интеграции теперь описан чеклистом в
[documentation/content-pipeline.md](documentation/content-pipeline.md) — по местам, где система
объявляет себя в Astro. Что мёртвый инструментарий не отрастёт снова, держит гейт
`scripts/test_doc_links.mjs`: путь к скрипту, скиллу или workflow, названный в документации или
в скилле, обязан существовать.

- **Раскладка:** Astro-приложение в отдельной папке **`web/`**. `src/` репо — это Markdown-контент
  (`src/{game}/{version}/{en,ru}/*.md`), вход контентного пайплайна — **не трогать**. Content collections
  Astro ссылаются на `src/{game}/...md`. Динамические роуты `/{lang}/{game}/{version}/{...slug}` через
  `getStaticPaths` (статика). Markdown рендерится **на билде**, не в браузере.
- **Интеграции:** `@vite-pwa/astro` (PWA — обязателен), **Pagefind** (статический поиск),
  `@astrojs/sitemap`. i18n EN/RU + hreflang, sitemap, JSON-LD. React в стеке НЕТ: компоненты
  дизайнера перенесены как `.astro`, островов в проекте ни одного (ревью #297) — если он
  понадобится, это отдельное решение, а не «уже подключено».
- **SEO-воронка:** CTA-блок «в лист персонажа» на каждой странице; событие Analytics на клик CTA.

### Параллельные прогоны: слот портов (Table#469)
Порты считаются от слота `OMNISGM_SLOT` (целое 0–3, дефолт 0): e2e-preview — **4321 + слот × 10**,
`npm run dev` — **4381 + слот × 10**. Вся арифметика в `web/e2e/ports.ts`. Основной каталог
остаётся на привычном 4321; соседнему worktree довольно `OMNISGM_SLOT=1` — и два прогона (как и
два dev-сервера) идут одновременно, не мешая друг другу.

Зачем: `reuseExistingServer` здесь ценен (команда сервера — полная пересборка сайта), но без
развода портов Playwright молча цепляется к preview соседнего каталога, и матрица идёт против
чужой ветки — зелёное по чужой сборке.

**Страховка одна — страж** `web/e2e/global-setup.ts`: сверяет каталог владельца порта и падает
внятной строкой до первого теста. `strictPort` стоит только у **dev**-сервера; у preview его
поставить нельзя — Astro не прокидывает `vite.preview` в preview-сервер, и такая настройка была
бы мёртвой (проверено: с занятым портом `astro preview` уезжает на соседний независимо от неё).

Вторая проверка стража — **свежесть сборки** (#251). Каталога мало: при `reuseExistingServer`
Playwright, получив ответ по HTTP, возвращается ДО запуска команды `webServer`, то есть
`npm run build` не выполняется. Поднятый час назад preview продолжает отдавать `dist`,
собранный из кода, которого в дереве уже нет.

Сверять сервер с `dist` для этого бесполезно — проверено экспериментом: `astro preview` читает
файлы с диска на каждый запрос, и такая сверка сходится всегда. Поэтому сравнивается отпечаток
**исходников**: `web/scripts/build_fingerprint.mjs` снимает его в `prebuild`, `postbuild` кладёт
снимок в `dist/build-id.txt`, а страж пересчитывает и сверяет. Две фазы, потому что при подсчёте
только в `postbuild` открыто окно: файл, сохранённый во время сборки, попал бы в отпечаток, но
не в `dist`, и страж вечно молчал бы про эту правку.

Входы: `web/src`, `web/public` и контент `src/` в корне — по «путь + размер»; `web/src/lib`,
`web/scripts`, `astro.config.mjs`, `package.json`, `package-lock.json`, `tsconfig.json` и
`web/.env` — чтением целиком (там правка «символ на символ» меняет вывод, не трогая размер).
За бортом намеренно: `.github/**` и `generate_api.py` — они собирают JSON API при деплое и в
локальный `dist` не попадают. Считается за ~50 мс.

Нет отпечатка в `dist` — страж падает, а не молчит: так выглядит сборка до #251 или сделанная
мимо `npm run build`, и это ровно то состояние, в котором проверка бесполезна.

Чего страж по-прежнему не умеет: он не спрашивает сам сервер. Свой `npm run dev`, окажись он на
порту e2e, был бы переиспользован молча — поэтому у dev и заведена своя база порта (`DEV_PORT`).

### Даты контента для JSON-LD (#219)
`datePublished`/`dateModified` у `Article` берутся из **истории git** по исходному markdown:
`web/scripts/gen-content-dates.mjs` (prebuild) делает один проход `git log --name-only` по `src/`
и пишет карту в `web/src/data/content-dates.json` (gitignored), а `web/src/lib/content-dates.mjs`
отдаёт даты странице. Сущностная страница знает свой ресурс и передаёт `contentSource` в
`ReaderShell`; какие `.md` стоят за ресурсом — говорит `_sources.json` от парсера
(`generate_api.py --emit-sources`), чтобы это знание не дублировалось в JS.

**Мелкий клон дат не даёт.** `actions/checkout` без `fetch-depth: 0` не привозит историю, и
страницы остаются БЕЗ дат — намеренно: дата билда на 6000 страницах означала бы «всё обновилось
разом». Поэтому в `ci.yml` и `deploy.yml` стоит `fetch-depth: 0` + `filter: blob:none`, а гейт
`verify_dist_meta_budget.mjs` валит сборку, если Article остался без обязательных полей.

### lastmod в sitemap (#221)
Проставляется postbuild-скриптом `web/scripts/add_sitemap_lastmod.mjs`: он читает `dateModified`
из JSON-LD уже собранных страниц (#219) и вписывает `<lastmod>` в `dist/sitemap-N.xml`. Так
маршрутизация и карта «URL → исходный файл» нигде не дублируются — sitemap и разметка страницы
согласованы по построению. Скрипт идемпотентен и валит сборку, если дат нет вовсе или они
пропали больше чем у 1% URL (без даты законно только языковые хабы — у них нет `Article`).

### Хабы уровня документа (#230)
`/{lang}/{game}/{version}/` — страница самой редакции: оглавление всех разделов (классы
разворачиваются списком) плюс справочники с числом сущностей. Шаблон один —
`web/src/components/DocHub.astro`, страницы-маршруты тонкие (по одной на игру). Ссылки строятся
из того же NAV-дерева, что и сайдбар, числа — из `meta.json` того же JSON API, что кормит сами
страницы: второго источника правды не заводим. Даты для JSON-LD — по ВСЕМ файлам документа
(`datesForDoc`), потому что своего markdown у хаба нет.

Зачем: по аудиту 2026-09-01 главный дефицит сайта — краулинг («обнаружена, не проиндексирована»
5 807 URL из 5 975), а верхнего узла структуры не было вовсе. Крошка документа с #230 ведёт
на хаб (раньше — на «первую содержательную страницу», компромисс варианта 2 из #220).
Уровень системы (`/{lang}/dnd/`) собственной страницы НЕ имеет — 301 на свежую редакцию
в `firebase.json`: у D&D две редакции плюс конверсионный документ, честного содержимого для
такой страницы нет.

### Эмулятор Firebase ≠ прод по синтаксису редиректов (#230)
Эмулятор матчит `source` через path-to-regexp и понимает ограничения вида `/:lang(en|ru)`;
**продовый Hosting их не понимает** — правило молча не срабатывает, URL отдаёт 404. Поймано
на редиректах уровня системы: на эмуляторе все три вели куда надо, после релиза `/ru/dnd`
вернул 404. Пишем маршруты явно (по одному правилу на язык) либо через ключ `regex` (RE2),
а **проверяем после деплоя на самом проде** — зелёный эмулятор здесь ничего не доказывает.
(Для заголовков эмулятор по-прежнему авторитетен: слияние правил по ключам совпадает.)

### Security-заголовки (#218)
`X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, HSTS и CSP (пока Report-Only)
ставятся в `firebase.json` — правило `hosting.headers` с `source: "**"`, первым в списке, а НЕ
в Cloudflare Transform Rules: конфиг в репозитории виден в ревью и едет вместе с деплоем.
Firebase мержит правила по ключам, поэтому точечные `Cache-Control` (`/img/**`, `sw.js`) живы —
это и проверяет `bash web/scripts/check_security_headers.sh` (без аргумента — прод, с URL —
эмулятор). HSTS без `preload`: список принимает апекс `omnisgm.com` и накрывает ВСЕ поддомены,
так что preload — отдельное решение владельца на лендинге, не отсюда.

**CSP в enforce с #225.** Инвентаризация источников — `node web/scripts/check_csp.mjs` (без
аргумента — по проду, с URL — по локальной сборке, политика подставляется из `firebase.json`).
Гонять надо ИМЕННО по проду: Cloudflare вставляет в HTML свой beacon
(`static.cloudflareinsights.com`) на эдже, в origin-ответе его нет, а локально ещё и не
грузится аналитика (нет `PUBLIC_*` ID в `.env`). И главное про метод: **нарушения CSP пишет
сам браузер, через API чтения консоли они не видны** — ловить надо событие
`securitypolicyviolation`, слушателем, поставленным до скриптов страницы. Регрессию держит
`web/e2e/csp.spec.ts` (политика из `firebase.json` подставляется в ответы preview).

**Динамические теги гейт не ловит.** e2e видит только то, что лежит в нашем бандле, а
`report-to`/`report-uri` в политике нет — значит нарушение на проде происходит МОЛЧА (тег не
работает, в консоли пользователя ошибка, у нас ни звука). Поэтому правило: **добавил тег
в GTM, включил новый режим Метрики или подключил внешний сервис — прогони
`node web/scripts/check_csp.mjs` по проду.** Минута работы против «аналитика молчит, и никто
не знает почему».

### Cloudflare: правка только заголовков не доезжает без сброса зоны (#227)
Дифф сборки (по нему строится purge-список и стриминг IndexNow) считает сигнатуру
**содержимого** страницы. Правка `firebase.json` тела страниц не меняет → список пуст →
чистить нечего, а Cloudflare при истечении TTL ревалидирует запись по ETag, получает `304`
и **оставляет ранее сохранённые заголовки**, сбрасывая возраст записи. «Подождать TTL» не
помогает: горячая страница держит старый набор сколько угодно (поймано на #218 — часть прода
была с security-заголовками, часть без). Поэтому шаг «Purge Cloudflare cache» в `deploy.yml`
сбрасывает **зону целиком**, если в деплоящемся диапазоне коммитов менялся `firebase.json`
(или вручную — `workflow_dispatch` с `purge_all`). Цена: зона одна на весь `omnisgm.com`,
заодно прогреются News и Table; правка заголовков редка, а частичное состояние прода хуже.

Отсюда же правило проверок: **мету, схему и заголовки после релиза проверять по origin**
`omnisgm-rules.web.app`, а не по `rules.omnisgm.com` — иначе валидатор (Rich Results Test,
`check_security_headers.sh`) читает застрявшую у CF копию и даёт ложный минус.

### Картинки сущностей и генератор (#201, #202)
Портреты существ и иконки заклинаний/магпредметов лежат в репо статикой (`web/public/img/{game}/{kind}/`),
показываются на странице сущности и уходят в поле `image` JSON API. Формат и раскладка —
`documentation/entity-images.md`, промты — `documentation/image-prompts.md`. Генератор: `scripts/gen-images.mjs`
+ `.github/workflows/gen-images.yml` (codex на подписке, очередь от данных Rules, ветка `images-queue`
→ draft-PR без автомёржа).

**Сдвиг вёрстки от картинок держит `web/e2e/layout-stability.spec.ts`** — CLS (тот же расчёт,
что у Core Web Vitals) на шаблонах с картинкой, десктоп и мобилка, бюджет 0.1. Место под портрет
резервируют ОБА слоя: grid-колонка в `EntityHead.astro` (168/92 px) и атрибуты `width`/`height`.
Из-за этого CLS остаётся нулевым, даже если убрать один слой, — убирать всё равно нельзя,
атрибуты работают до применения CSS.

Тонкость метода: **без троттлинга такой тест зелёный по построению** — с localhost картинка
приезжает раньше первой отрисовки, сдвигу неоткуда взяться. Отсюда эмуляция Fast 3G через CDP
и отдельный контрольный тест на синтетической странице без резерва места: если измеритель
перестанет видеть сдвиг, красным станет он, а не «всё хорошо». В контроле текста на целый
экран не для красоты — CLS это доля площади × дистанция, на паре строк сдвиг выходит 0.02
и проходит бюджет, хотя контент прыгнул на пол-экрана.

Замерять это по проду через PageSpeed Insights не выйдет: у публичного API общая анонимная
квота, регулярно исчерпанная (ловил 2026-09-01).

**Ранбук токена codex.** Держателей токена **двое** — CI News и CI Rules, оба от одного
локального `~/.codex/auth.json`. (Третьим был CI Table, пока там жил свой генератор портретов;
он снесён вместе с ним — Table#403.) Прогон падает с `refresh_token_reused` / `token_revoked` /
`401` — значит локальный перелогин обесценил токен в CI. Починка: `codex login` локально,
затем обновить секрет в ОБОИХ репозиториях:

### Связка setup в workflow — один общий шаг (#287)
`setup-node` + кэш + `npm ci` + `setup-python` живут в composite-действии
`.github/actions/setup-web`; workflow зовут `- uses: ./.github/actions/setup-web`. Версии Node
и Python объявлены ТОЛЬКО там (дефолты входов), а отказ от них пишется явно — `node-version: ''`
у джобы на одном Python. Держит `scripts/test_workflow_setup.mjs`:
он запрещает прямые `actions/setup-node`/`setup-python` в наших workflow и в composite-действиях,
запрещает свои литералы версий у вызывающих и требует `timeout-minutes` у каждой джобы (без него
зависший шаг держит очередь до дефолтных шести часов — `release` однажды упёрся в 360 минут).
Исключение одно: вендорный `claude-review.yml`.

### Локальные гейты и pre-commit
`npm run test:unit` (node-юниты), `npm run test:unit:py` (python-гейты), `npm run test:gates` —
всё сразу; состав сверяется с `ci.yml` стражем `scripts/test_unit_agenda.mjs`.

Хук подключается корневым **`npm install`** — именно в корне, без `--prefix web`: `npm ci
--prefix web` корневой `prepare` не выполняет, и хука не будет. Уже настроенный
`core.hooksPath` скрипт установки не трогает, а называет. Обойти хук — `SKIP_HOOK=1` или
`git commit --no-verify`.
