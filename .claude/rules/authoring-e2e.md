# Screenshots and the e2e run — rules for the code author

Continuation of `authoring-pitfalls.md` for repos with e2e. Before pushing, walk the list against your diff.

1. **Snapshots — no variable content.** Stabilize the date/text width/element order with a fixture or hide them without affecting geometry; do not use string comparison of outerHTML — it is both blind to copies and alarmed by harmless refactoring.
2. **A screenshot is taken where it means something: the shell by page, a tab by area, a widget by element.** The shell (navigation, header, tab bar, panel split) is guarded by ONE page screenshot per viewport — taken with `expect(page)` on any single screen; without it everything around the content falls out from under the guard. Shoot a tab or panel by the panel's own area on the **showcase** preset, which has one instance of each row kind and state: that way layout and content land in one screenshot, and a shell edit colours its own screenshot rather than the screenshots of all tabs at once. Shoot a widget with states (HP bar, status cell) by element. It is the AREA that narrows, not the matrix: the screenshot's number of projects stays the same, and the height still follows the content, without cropping. Before accepting a baseline, open it with your own eyes — is the last element (badge, caption, button) visible and is the frame in place: cropping looks like a legitimate border in the baseline. If it does not fit, look for the cause in the layout (on pages whose height follows the window, fitting the window does not converge: each step grows the content too) and file an issue for it, rather than hiding elements or cropping the screenshot. `fullPage` does not help: it stitches the scroll and stamps fixed elements into the middle.
3. **Re-shooting screenshots — with a check that the baseline changed.** A green `--update-snapshots` does not mean "baseline rewritten": the build cache (`node_modules/.vite`) serves the page old code, and the old screenshot passes against itself. After re-shooting, verify that the screenshot files really changed (`git status`, size), and on a mismatch with live geometry (`boundingBox` in DOM ≠ baseline) clear the cache, delete the baselines and shoot from scratch.
4. **Run completeness — from `--list`, not the sum of passes.** Split the matrix into several commands (out of memory, parallel slots) — compare the number of UNIQUE tests with `npx playwright test --list | tail -1` (`Total: N tests in M files`, the matrix is not executed). Two traps when adding up sums: a project dependency (`dependencies`) runs in EVERY pass and doubles the count, and a project forgotten in the `--project` list simply vanishes from the gate. The report gets the unique count and the commands themselves.
5. **A new control goes under the touch gate immediately (only where the gate exists: Table, `tests/e2e/touch-targets.spec.ts`).** A new `input`/`button`/`onClick`/modal in the diff — its testid appears in the scan in the same commit, sizes come from the repo's mixins (`touch-height`, `touch-hit-area`, `no-zoom-font`), not literals; a carrier that is not a `button`/`input` gets `role="button"`, otherwise the scan does not see it and a green gate means nothing (12 findings in the week of 22–28.09, five PRs in a row). In a repo without such a scan and mixins the rule does not apply. The scenario for a new interactive element is rule 19 of `authoring-pitfalls.md`.
