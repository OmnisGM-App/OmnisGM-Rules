# Common mistakes in our PRs — rules for the code author

<!-- COPY of the shared template: source of truth — OmnisGM-App/claude-plugins/templates/authoring-pitfalls.md;

     revised 2026-09-29 after the CI-review week of 22–28.09 (~470 findings): rules 1–4 and 6 turned into

Each rule is a class of error that review caught repeatedly. Before pushing, walk the list against your diff.
Where a rule has a command, the command's result is a number in the PR decisions line, not the word "checked". A command that is more than one line is a script in the omnisgm plugin (`plugins/omnisgm/scripts/checks/<name>.sh`, source: OmnisGM-App/claude-plugins), run from the repo root through its launcher, the same from any worktree and any machine that has the plugin: `bash "$(ls -d ~/.claude/plugins/cache/omnisgm/omnisgm/*/scripts/checks | sort -V | tail -1)/run.sh" <name> [<base>]` (`run.sh pr …` is `run_pr_checks.py`; below `CHECK <name>` stands for this whole command; in a claude-plugins checkout: `bash plugins/omnisgm/scripts/checks/run.sh <name>`): no output and exit 0 is clean, exit 1 prints the hits as `path:line:text`, exit 2 means the check itself broke (never a pass). Each script has a positive and a negative fixture run by a test there; a regex is fixed in the script, not copied into a rule.

Rules about screenshots and the Playwright run are moved to `authoring-e2e.md`, which lives in the repos with e2e (Table, News, Rules).
1. **Text twins.** What goes stale is not the new name but the OLD wording that is absent from the diff: a removed concept ("glyph" after the field was deleted), a former "the only/single", an old variant name, a module header listing its consumers. The most frequent class (~90 findings over the summer, 72 in the week of 22–28.09). Check: `twins-removed-tokens.sh <base>` (identifiers the diff removed and did not add back, searched across the whole tree except the diff's files; `TWINS_EXTRA="глиф значок"` adds the Russian synonyms of the removed concept, `TWINS_EXCLUDE=":(exclude,glob)src/**/*.md"` keeps the SRD prose of Rules out) and `twins-absolute-words.sh <base>` (uniqueness words — only, always, never, единственный, всегда — in the files the diff touches, that the change may have turned into a lie). The identifier grep does not see a removed MECHANISM named in words (a CI step called «check-run lifecycle», a header «the job stays green», «no synchronize trigger»): add its phrase to the search by hand — `git grep -inF "<old phrase>" -- .github docs scripts .claude '*README*'` (a pathspec is rooted: plain `README*` finds only the root one) — including workflow `name:` lines, step names and the headers of files outside the diff (Rules#447, #441, #452, News#171, #173, #160, #156 each left one). Give the Russian synonyms of the removed concept (глиф/значок, увеличение/масштаб — glyph/icon, zoom/scale) in `TWINS_EXTRA` — the perimeter is the same as for identifiers. Every hit is removed in the same commit or named in the decisions line with the reason it stays.
2. **Confirm the test by mutation — and name the failing case.** For every new branch and every new assert, three mutants: "revert the code to before the change", "remove the registration/line from the default list", "swap the block"; EXACTLY this test must go red, via the assert, not a TypeError. In the PR decisions line, one line each: «мутация: <что сломал> → <имя упавшего кейса>» (mutation: <what was broken> → <name of the failing case>); an assert without the failing case's name does not count as a gate. Forbidden forms that survived for weeks: `toContain('--variable-name')` and `toBeTruthy()` where the case name names the value (the name is checked, not the value); a reference imported from the module under test (`const OK = MODULE_CONST` — always green); a branch under `// Stryker disable`; a test written from the review's recipe without being run both ways.
3. **Cover the motivating branch in its live form — and prove by grep that it is under test at all.** Guard exactly the input the change was made for, in the form it exists in prod (find the value's producers by grep), not in a form convenient for the test. Half of the week's findings were not about form but about the new thing simply being absent from tests, or present only in e2e that CI does not run. Check: `new-id-ci-coverage.sh <base>` prints `name: ci=0 e2e=N` for every new `data-testid` and exported name that no CI test mentions as a whole token (`foo` is not covered by `foo-bar`; the e2e column is information, not coverage).
   `ci=0` is a finding, not "covered by a neighbouring test". A test living only in e2e outside CI (the `e2e` column) does not count as coverage — it goes into the blind-spot list of rule 14.
   **The wiring is part of the branch.** When a function gets a new parameter or a setting is read from config/env, the prod call site that passes it is a separate line the unit test of the function never reaches (the function's default hides a missing argument; a test passing `0.88` as a literal does not read the config). For each new parameter/setting: `git grep -n <param>` must show the prod caller AND a test that goes through the caller (or through the config reader) and goes red when the argument is dropped — mutant: delete the argument at the call site, name the failing case (~10 findings in 3 weeks: `minImportance`, `featureStorySimilarity`, `categories:`, `useRebuiltChoices` in the sheet, `og` tags).
4. **PR body — from the final head, with the hash.** The first line of the «Проверка/Gate» (Check/Gate) block in the PR body is `git rev-parse --short HEAD` on which the numbers were taken; before asking for a merge, compare it with `gh pr view N --json headRefOid`. A mismatch means the body is retaken; the order is strictly code → run → body, and any push after the numbers were taken makes the block stale. A checklist item is closed by an artifact (file in the diff, link), not by a word. **`Closes #N` is a claim about the issue, check it before the push** (16 PRs in 3 weeks got a medium for it):
   Before the push run `CHECK pr --repo <R> --pr <N> --only closes`: it reads every `Closes|Fixes|Resolves` target of the PR body (another repo's issue too, by `owner/repo#N` or URL) and lists its open `- [ ]` items — a moved item `~~…~~ ➡️ #N` (or `-> #N`) is not open, a bare struck item `~~…~~` without the arrow is (omnisgm-issue: close only when every item is `[x]` or moved). Any item listed means `Refs #N`, or tick/move the item first. After the push, before asking for the merge, the body names the live head:
   ```bash
   # after the push, before asking for the merge: the body names the live head
   gh pr view <N> --json headRefOid,body --jq '.headRefOid[0:7] as $h | "head \($h): in body = \(.body | contains($h))"'
   ```
   Open items listed (moved items excluded): tick each with the artifact (comment with the link) or write `Refs #N` instead of `Closes`. The `gh` line must print `in body = true`.
5. **Both sides of the invariant.** The gate checks both "the right thing is present" and "nothing extra/substituted"; in path operations normalize (realpath) and check BOTH sides — source and destination.
6. **Failure is loud, in tooling code too.** An external call (fetch/subprocess/file) checks success or fails with a clear message; NaN/undefined/empty input must not silently turn the check green. Diagnostics accumulate findings in a list rather than dying on an exception halfway, and print the root cause once; a `throw` inside a pass must not come before the artifact and history are written. In tests, `test.skip` and an early `return` on an unasserted predicate are forbidden — that is green instead of red. For a diff touching `.github/workflows/**` or `scripts/**`: a step with a pipe runs under `shell: bash` (pipefail), no `return`/`exit 0` before the return code is checked. **A fallback must not merge two states.** `x=$(cmd) || x=none`, `|| line="pending "`, `|| live=` turn "the API failed" into the same value as "nothing there yet" or "still pending", and the next branch acts on it (a gate that waits forever, a rerun that cancels a live run; 6 PRs in 3 weeks). Check: `fallback-merges-state.sh <base>` (added `x=$(cmd) || x=…` also in a brace group or with the fallback on the next line, `|| true`, `|| :`, `|| echo`, `|| exit 0`) and, for `.github/workflows/*.yml` and `*.sh`, the `fallback` check of `ci_lint.py` (`x=$(cmd) || x=…` only when the value is one a real result can also have — empty, `0`, `[]`, `{}`, `none`, `pending`…; a distinct sentinel such as `ERR` or `000` that the next branch tests, a plain `[ … ] || x=…` and a status capture `|| rc=$?` pass; allowed by a `# fallback-ok: <why>` comment on the line or above it) — every hit either fails loudly, or carries a distinct sentinel (`ERR`) that the next branch handles separately, and a test/mutant that feeds the failing call. A green vitest is `EXIT=0` AND `Errors 0`, not "N passed": an unhandled rejection (a `vi.mock` that lacks a newly added export) fails the CI step while the pass count looks fine (Table#1122). Run it as `npx vitest run > log; echo EXIT=$?` and grep `Errors|EXIT`; when you add an export to a module, find its mocks first (`grep -rln "entities/<module>'" --include='*.test.*' | xargs grep -l vi.mock`) and extend them.
7. **A new file goes under the gate immediately.** Include a new script/module in tsc/test glob/lint right away; verify the CI step actually runs on the needed trigger and BEFORE the critical operation (deploy), not after it and not under unreachable conditions. Check: `new-test-file-wired.sh <base>` lists every NEW test file (`test_*.py`, `test_*.mjs`, `*_test.py`, `*.test.{js,jsx,ts,tsx,mjs,cjs,mts,cts}`) that no workflow and no package.json runs — named there, matched by a glob there, or collected by a runner that discovers tests (`unittest discover`, `pytest`, `vitest`, `jest`, `node --test`, `playwright test`); the file's own docstring is not a CI step. It does not read triggers or exclude lists, so for each file that passes, read the CI step: it must run on `pull_request`, and a hit only in an exclude list (`workflows.test.js` skipping the file) or `skipTest`/`skip` on "file not found" is the finding — a rename then turns the only check into a skip (5 PRs in 3 weeks: `test_merge_gate.py`, `WorkflowContract`).
8. **Guarantee by code, not text.** "Do not merge", "read-only", "do not ping on zero" is a checkable condition in code/CI; a comment line or an instruction gets bypassed without a single violation.
9. **Fix the class, not the occurrence.** Found a defect — grep the same pattern across the whole repo: a neighbouring file with the same flake/bug is part of your own fix.
10. **Anchors by running, not from memory.** Verify every factual argument ("X is not implemented", "the formula is computed in place", line/module counts) against the code at the current head; a document written from memory of the project gets rewritten after the very first review.
11. **Relaxations are targeted.** A normalization/exception introduced for a specific case is limited to that case (flag, version, pin with an application counter) rather than weakening the gate for all data.
12. **Regex — for variability and with boundaries.** Run the gate's parser/regex on all realistic spellings of one construct (case, quotes, markup, a comment on the same line); set boundaries — `max-age=0` must not match `086400`.
13. **One source of truth.** Logically linked values (export list ⇔ implementation, threshold ⇔ docstring, block ⇔ file name) are derived mechanically from one place — two literals will drift apart on the next edit.
14. **Name the gate's blind spots.** In the PR body explicitly list the regression classes that green CI does NOT catch (e2e not in CI, exports/files unchecked, snapshots ignored) — silence reads as full coverage.
15. **New input — across all consumers.** Added a union variant, a field of a shared type, a mode, an option or a prop, changed cardinality (single → set) — grep and list ALL consumers of the type and all display sites (labels, print, export, projections) and for each say in the PR body what happened to it; "worked on the single" is not an answer about the set. The largest uncovered class of the week (~22 findings; one PR yielded six).
16. **A parallel branch — the same caveats; new things follow the neighbour.** A new branch next to an existing one (a disabled effect next to an active one, its own speed next to the base one) inherits ALL filters, clamps and floors of its neighbour — write out the neighbour branch's caveats as a list and check each one on yours. A new file, locator, migration, form of the same kind — open the neighbour and repeat its guards and fields; name any divergence in the thread as deliberate (~17 findings).
17. **Dead remainder and the second side of a declaration.** Removed the last consumer — remove the prop, export, locale key, constant, context field, mock in the same commit. New export, type, locale key, readable field — grep the second side (the consumer; for a readable field, the prod writer): `git grep <name>` with a single hit, the declaration, is a finding, "for the future" is not an argument, a unit test passing the option by hand does not count as the second side (~19 findings; one PR yielded this class four rounds in a row).
18. **Round trip and degenerate input.** A form that opens a saved record returns it unchanged: open → "Save" with no edits → the document is byte-identical; verified by a unit test "data → draft → build → replace", not only via the "new record" path. An empty string, `[]`, `{}`, a fan-out to zero addresses, equal numbers are not "filled in": choose the branch by length, not truthiness, and run every new build on degenerate values (~15 findings, two ❗ in one PR).
19. **New interactive element — by scenario, not by build.** Run a clickable element end to end: repeated press, write rejection, `disabled` (the `:disabled` rule on the class and globally, the dead zone under an enlarged hit area), Enter on an empty field, Esc, arrows past the list edge, a list taller than the window, a column narrower than its content, language switch on the fly, neighbours in the same flex row. Screenshots and unit tests do not see this unless the fixture has such an input (~13 findings in the week).
20. **A tool's contract — by running it, not by recalling it.** A CLI flag, an API field, a login format, a status value, a default that a config key replaces: run the exact command once against a real object and paste the output into the PR body before building on it. Table#1179 spent one review round on `gh api --arg` (no such flag), `app/dependabot` vs `dependabot[bot]`, three-dot `compare` and a missing `permissions:` entry — each a fact one run would have shown. Workflow- and gh-specific facts: `authoring-workflows.md`.
21. **Fix the twin of the fix.** A review recipe names one place; the same construct usually has a sibling in your own diff (the second label, the second right, the second branch). Before pushing a fix round, grep the diff for the pattern you just changed and apply the fix to every sibling or say in the thread why the sibling differs. Two rounds of #1179 were the sibling of the previous round's fix.
22. **Re-walk the scenario ledger after every fix round.** A fix for one scenario can undo another (unlabeled → forced round → base-merge mode → label never returns). Keep the list of scenarios the design must survive in the PR body and, after each change, state for each one how it still holds — a fix that is not re-checked against the ledger is the next round's ❗.
23. **New persisted state — its lifecycle is the scenario ledger, written before the first push.** A new field, flag or map entry that one write sets and later writes must respect (a pending action, a "done" marker, a cached decision): list every event that touches the record and decide each in code and in a unit case — created; repeated; an unrelated later write to the same document (another apply, healing); undo of the creating write and of a later one; the terminal state of the subject (0 HP, death, deletion, expiry by a worker); owner or access change; the thing it refers to replaced or ended; a concurrent writer of the same document. Decide from a snapshot taken at the event (what held at the damage), not from the current state at render; store only what cannot be derived from immutable sources; write map entries by field path, so a concurrent write to a sibling key survives. A record that a guard hides must not also be deleted by that guard if an undo can lift it. Table#1182 (one review slice) took five rounds — each ❗ was one of these events, found one per round.
24. **A game-rule fact — from the rules text of the right edition, before code.** "What counts as one source", a cap, a rounding: quote the sentence from the SRD of the edition the sheet implements (OmnisGM-Rules `src/dnd/srd-5.2` vs `srd-5.1`) in the PR body; a rule recalled from another edition reads plausibly and is wrong (Table#1182 quoted the 2014 «separate saving throw for each source» as 2024). A rule the text leaves open — a question to the owner before the code, not in the fourth review round.
25. **A write after an `await` decides from the live state, not from the snapshot taken before it.** A read of the compendium, a network call, a confirm window: while it runs, the sheet changes (another edit, a second device, the user's own next click, an Undo). The most frequent ❗ of the sheet flows (15 PRs in 3 weeks: class apply/remove/update, origin apply, lineage, bulk update). Check: `await-snapshot.sh <base>` lists every added `await` as `path:line:text` — for every hit list the values read BEFORE the await and used AFTER it (`basis()`, a captured `character`, `before`, a closure `pending`, an `onChange` captured at the click). Each such value is re-read after the await (`basis()` again, a ref), or compared with a token (`seq`/`latest.current`/the document revision) and the stale answer is dropped with a visible message, not silently. A unit case holds a deferred promise, changes the document before resolving it and asserts that the write kept the change; a second case does the same for Undo and for the second pick of the same field. Mutant: replace the live read with the snapshot — that case goes red.
26. **Check your own commit before the push — every commit, not only review fixes.** Order: edit → commit, do not push → look for new problems the commit created → found one: fix and commit → only then push (owner, 2026-11-08, after claude-plugins#37: the fix of a round-2 ❗ compared all of `templates/`, the trigger and the script only `templates/*.md`, and round 3 found the new ❗ the fix had made). Simple checks are enough, not a full plugin review: `git diff` of the commit, then (a) for every changed condition, which other inputs now behave differently — neighbour paths, other triggers, the file or event set of the adjacent steps; (b) run the finding's scenario AND one neighbour case the change could break (a grep, a unit test, a stub); (c) write «checked» in a thread or the PR body only after the command really ran and its output says so — a command that failed is not a check.
